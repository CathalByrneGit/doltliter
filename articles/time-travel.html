Time travel: history, diffs and blame

Committing data is only half the point. The other half is being able to ask what the data used to be, what changed between two moments, and who changed it.

library(doltliter)

con <- DBI::dbConnect(Doltlite(), tempfile(fileext = ".db"))
dolt_config(con, user.name = "Ada Lovelace", user.email = "ada@example.com")

Let’s build a table with a few revisions behind it. The primary key matters here: dolt_blame() needs one, because without a stable row identity there is nothing to attribute a change to.

DBI::dbWriteTable(
  con, "readings",
  data.frame(id = 1:3,
             sensor = c("A", "B", "C"),
             value  = c(10.0, 20.0, 30.0)),
  field.types = c(id = "INTEGER PRIMARY KEY")
)
dolt_commit(con, "First calibration run")

DBI::dbExecute(con, "UPDATE readings SET value = 21.5 WHERE id = 2")
#>[1] 1
dolt_commit(con, "Recalibrate sensor B")

DBI::dbExecute(con, "INSERT INTO readings VALUES (4, 'D', 40.0)")
#>[1] 1
dolt_commit(con, "Add sensor D")

dolt_log(con)[, c("committer", "date", "message")]

dolt_diff() works one level up — which tables changed in each commit, rather than which rows:

dolt_diff(con, "readings")[, c("commit_hash", "data_change", "schema_change")]
commit_hash data_change schema_change
43b3afc0f07610cc33d0277d5f04a6bc788ef2ab 1 0
da8a241083c016c66eed3a0b2a997ef279f8cfdb 1 0
00fc5db429e266a193f55449d9d32b3494d70cdb 1 1

Uncommitted work shows up under the pseudo-commit WORKING, which is a convenient way to see whether anything is pending:

DBI::dbExecute(con, "UPDATE readings SET value = 41.0 WHERE id = 4")
#>[1] 1
dolt_diff(con, "readings")$commit_hash[1]
#>[1] "WORKING"
dolt_status(con)
table_name staged status
readings 0 modified

2 Row-level diffs

dolt_table_diff() is the workhorse. Give it two endpoints and it returns one row per changed row, with from_ and to_ columns side by side:

d <- dolt_table_diff(con, "readings", from = "HEAD", to = "WORKING")
d[, c("diff_type", "to_id", "from_value", "to_value")]
diff_type to_id from_value to_value
modified 4 40 41

Endpoints are anything DoltLite understands as a ref — a branch, a tag, a commit hash, HEAD~2, WORKING:

dolt_table_diff(con, "readings", from = "HEAD~2", to = "HEAD")[
  , c("diff_type", "to_id", "from_value", "to_value")]
diff_type to_id from_value to_value
modified 2 20 21.5
added 4 40.0

A range string works too, which is handy when comparing branches. Two dots are the two endpoints; three dots is merge-base to the right endpoint:

dolt_table_diff(con, "readings", range = "main..feature")
dolt_table_diff(con, "readings", range = "main...feature")

For a summary rather than the rows themselves:

dolt_diff_stat(con, "HEAD~2", "HEAD")
table_name rows_unmodified rows_added rows_deleted rows_modified cells_added cells_deleted cells_modified old_row_count new_row_count old_cell_count new_cell_count
readings 2 1 0 1 3 0 1 3 4 9 12 
dolt_reset(con, "hard")

3 Reading the past directly

dolt_at() reads a table as it was at some revision — no checkout, no branch switching, just a query against a historical snapshot:

lg <- dolt_log(con)
first <- lg$commit_hash[lg$message == "First calibration run"]

dolt_at(con, "readings", first)
id sensor value
1 A 10
2 B 20
3 C 30 
DBI::dbReadTable(con, "readings")
id sensor value
1 A 10.0
2 B 21.5
3 C 30.0
4 D 40.0

dolt_history() goes wider: every version of every row across the commit ancestry, with the commit metadata attached. It is the right tool for “plot this value over time”:

h <- dolt_history(con, "readings")
h[h$id == 2, c("id", "sensor", "value", "commit_hash")]
id sensor value commit_hash
2 B 21.5 43b3afc0f07610cc33d0277d5f04a6bc788ef2ab
2 B 21.5 da8a241083c016c66eed3a0b2a997ef279f8cfdb
2 B 20.0 00fc5db429e266a193f55449d9d32b3494d70cdb

4 Who changed this row

dolt_blame() attributes each live row to the commit that last set it:

dolt_blame(con, "readings")[, c("id", "committer", "message")]
id committer message
1 Ada Lovelace First calibration run
2 Ada Lovelace Recalibrate sensor B
3 Ada Lovelace First calibration run
4 Ada Lovelace Add sensor D

It walks first parents from HEAD. Schema-only changes such as ALTER TABLE ... ADD COLUMN do not update blame, so a column addition will not make every row look freshly touched.

5 Content hashes

Every table root and the catalog as a whole are content-addressed, and the table and database hashes are history-independent: the same rows hash the same regardless of how they got there.

dolt_hashof(con, "HEAD")        # commit hash — covers the timestamp too
#>[1] "43b3afc0f07610cc33d0277d5f04a6bc788ef2ab"
dolt_hashof_table(con, "readings")
#>[1] "6cf508013fc3b1e71c3686c3d24fcb1ab0a78d02"
dolt_hashof_db(con)
#>[1] "b39b752292634f8afaac792b6302126f1ae80874"

That makes dolt_hashof_table() a cheap way to ask “did this table actually change?” across two databases or two points in time, without diffing.

6 Generating a patch

dolt_patch() turns a diff into ordered, executable SQLite statements — useful for review, or for replaying a change somewhere else:

p <- dolt_patch(con, "HEAD~1", "HEAD")
p[, c("statement_order", "diff_type", "statement")]
statement_order diff_type statement
1 data INSERT INTO “readings”(“id”,“sensor”,“value”) VALUES (4,‘D’,40); 
DBI::dbDisconnect(con)
